Slopsquatting: How AI Hallucinations Create Software Supply-Chain Risks

By PurpleLotus Research Oct 10, 2026 4–5 min read

What Is Slopsquatting?

AI coding assistants help developers write code faster, but they can sometimes recommend software packages that do not exist.

This becomes a security risk when an attacker registers one of these invented package names and publishes a malicious version. If a developer or AI coding agent installs it, the package could introduce malicious code into the development environment.

This technique is known as slopsquatting. Unlike traditional typosquatting, which exploits spelling mistakes, slopsquatting targets package names hallucinated by AI systems.

How Does a Slopsquatting Attack Work?

A typical attack follows four steps:

  1. AI generates a package name: A coding assistant recommends a library that does not exist.
  2. An attacker registers it: The attacker publishes a package under that name on a registry such as npm or PyPI.
  3. A developer installs it: The developer trusts the AI-generated recommendation and runs the installation command.
  4. Malicious code executes: Depending on the package and its permissions, it may attempt to steal credentials, access sensitive files, or compromise a build pipeline.
An AI-generated recommendation is not proof that a package is legitimate.

Recent Research and Real-World Evidence

1. USENIX Security 2025: Package hallucinations

Research presented at USENIX Security 2025 examined 576,000 code samples generated by 16 language models. The researchers reported hallucinated-package rates of at least 5.2% for the commercial models studied and 21.7% for the open-source models studied.

The research demonstrates that nonexistent package recommendations are a measurable problem. These figures describe generated code, not the percentage of malicious packages or compromised systems.

Source: USENIX Security 2025 research

2. January 2026: The react-codeshift case

Aikido Security researcher Charlie Eriksen reported that the nonexistent npm package react-codeshift appeared in 237 GitHub repositories through AI-generated agent-skill instructions and their copies.

The researcher registered the package defensively after discovering that AI agents were attempting to install it. The case demonstrated how hallucinated package names can spread and trigger real installation attempts.

Important: The registered package was a safe placeholder. The report did not establish a malware infection or successful compromise.

Source: Aikido Security investigation

What do these findings mean?

AI-generated package names can spread across repositories and automated development workflows. If attackers register those names first, developers may unknowingly install malicious dependencies.

The evidence supports treating dependency verification as a necessary security control, rather than assuming every AI recommendation is trustworthy.

Why Traditional Security Scanners May Miss It

Traditional vulnerability scanners often focus on known CVEs and documented security weaknesses. A newly published malicious package might have no known CVE and may not appear in vulnerability databases.

An SBOM can accurately record that package without determining whether it is trustworthy. Similarly, a KEV check may return no match because the package is not associated with a listed exploited vulnerability.

Each tool serves a different purpose:

SBOMIdentifies software components.
Vulnerability scanningDetects known vulnerabilities.
KEV monitoringIdentifies vulnerabilities listed as known exploited.
Slopsquatting detectionInvestigates suspicious or untrusted dependencies, including those introduced through AI-generated recommendations.

These controls complement one another.

How Organizations Can Prevent Slopsquatting

Organizations can reduce the risk by introducing several practical controls.

  • Verify package identity: Check registry existence, package ownership, version, and source repository.
  • Investigate suspicious packages: Review unfamiliar names, publication history, maintainers, and provenance.
  • Use lockfiles and integrity checks: Reduce unexpected dependency changes and verify package contents against recorded integrity information.
  • Inspect installation behavior: Review lifecycle scripts and restrict unnecessary filesystem and network access.
  • Secure CI/CD pipelines: Scan new dependencies in pull requests and require approval for suspicious packages.
  • Restrict AI agents: Require verification before agents install dependencies or execute untrusted commands.

A newly published package is not automatically malicious. Security decisions should be based on multiple indicators and supporting evidence.

Slopsquatting and the Cyber Resilience Act

The EU Cyber Resilience Act establishes cybersecurity requirements for products with digital elements, including vulnerability handling and lifecycle security.

Slopsquatting is relevant to software supply-chain risk management, but detecting it alone does not establish CRA compliance. Organizations must assess the applicable requirements and maintain appropriate security, vulnerability-handling, and reporting processes.

Conclusion

Slopsquatting demonstrates how an AI-generated mistake can become a software supply-chain security risk.

Recent research and the react-codeshift investigation show why package verification matters, particularly as AI coding agents increasingly automate development tasks.

Organizations should combine SBOM management, dependency verification, vulnerability intelligence, and CI/CD security controls to reduce the risk of installing untrusted packages.

AI can accelerate software development, but dependency trust must always be independently verified.
